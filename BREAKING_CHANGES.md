# Breaking-Change Taxonomy

This document is normative. The diff engine MUST emit exactly these rule IDs, severities, and `breaking` flags. Any new rule requires a new ID and a fixture.

---

## 1. Severity definitions

| Severity | `breaking` | Definition | Consumer impact |
|---|---|---|---|
| `critical` | `true` | Breaks an existing consumer that follows the previous contract | Request rejected, response unreadable, or behavior silently wrong |
| `warning` | `false` | May cause issues or requires attention, but does not break a conforming consumer | Data loss, changed defaults, weaker guarantees, deprecation |
| `info` | `false` | Non-breaking, additive, or metadata-only | None; safe to ignore |

`breaking` is always derived: `breaking = (severity == "critical")`. Store both for query convenience; enforce consistency with a database check.

### Severity precedence

- All applicable rules are emitted. A single location may produce more than one change (for example a field type change and an enum change).
- Identical fingerprints are merged.
- The diff summary counts each surviving change.
- If a change is ambiguous, use the **less severe** rule and document why; false criticals destroy trust faster than false warnings.

---

## 2. Comparison algorithm

1. Require two parsed, normalized versions of the same spec.
2. Index endpoints by `key` (`METHOD path`). Keys present only in `from` → `BR-001`. Keys only in `to` → `BR-002`.
3. For common keys, compare `operationId`, `deprecated`, `parameters`, `request_body`, `responses`, and `security`.
4. Compare parameters by `(in, name)`.
5. Compare schema trees recursively using the normalized component map.
6. Compare response status keys after success-status normalization.
7. Compare referenced components and security schemes.
8. Emit metadata-only changes last.
9. Deduplicate by fingerprint; sort by severity, path, method, fingerprint.

Diffing never re-parses YAML and never compares raw text.

## 3. Rule catalog

### 3.1 Operations

| ID | Change | Severity | Detection |
|---|---|---|---|
| `BR-001` | Operation removed | critical | Endpoint key exists in `from`, not in `to` |
| `BR-002` | Operation added | info | Key exists in `to`, not in `from` |
| `BR-003` | `operationId` changed | info | Both keys exist and `operation_id` differs; clients generated by operationId may churn |
| `BR-004` | Operation deprecated | info | `deprecated` false/absent → true |
| `BR-042` | Metadata-only change | info | `summary`, `description`, or `tags` changed with no structural change |

**Guard:** adding an operation is additive and MUST NOT be critical, even though it changes the document.

### 3.2 Parameters

Parameters include `path`, `query`, `header`, and `cookie` locations.

| ID | Change | Severity | Detection |
|---|---|---|---|
| `BR-005` | Required parameter added | critical | New `(in,name)` with `required=true` |
| `BR-006` | Optional parameter added | info | New `(in,name)` with `required=false` |
| `BR-007` | Parameter removed | warning | Present in `from`, absent in `to`; clients may still send it |
| `BR-008` | Parameter became required | critical | `required` false/absent → true |
| `BR-009` | Parameter became optional | info | `required` true → false |
| `BR-010` | Parameter type changed | critical | Normalized `schema.type` differs |
| `BR-011` | Parameter enum narrowed | critical | `enum(to)` is a strict subset of `enum(from)` |
| `BR-012` | Parameter constraint tightened | warning | New/changed `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `minItems`, `maxItems` that only reduces the accepted set |

**Guard:** path parameters are always required in OpenAPI; flipping `required` on a path parameter is invalid input and is reported as `ERR-1201`, not a rule.

### 3.3 Request body

| ID | Change | Severity | Detection |
|---|---|---|---|
| `BR-013` | Request body became required | critical | `required` false/absent → true |
| `BR-014` | Request body became optional | info | `required` true → false |
| `BR-015` | Request field removed | warning | Property exists in `from`, absent in `to`; server may ignore silently |
| `BR-016` | Required request field added | critical | New property listed in `required` |
| `BR-017` | Optional request field added | info | New property not in `required` |
| `BR-018` | Request field type changed | critical | `schema.type` differs, including array↔object |
| `BR-019` | Request field format changed | warning | `format` differs while `type` is unchanged |
| `BR-020` | Request enum narrowed | critical | `enum(to)` is a strict subset of `enum(from)` |
| `BR-021` | Request enum widened | info | `enum(to)` is a strict superset of `enum(from)` |
| `BR-022` | Request field became non-nullable | critical | `nullable` true → false/absent |
| `BR-023` | Request constraint tightened | warning | New/changed constraint that only reduces the accepted set |
| `BR-024` | `additionalProperties` false | warning | true/absent → false on a request object |

**Guard:** a request field that is added as required inside a condition (`oneOf` branch) is critical only if that branch was already the only valid branch. Branch-local additions are `warning` (BR-023) unless the whole union collapses.

### 3.4 Responses

| ID | Change | Severity | Detection |
|---|---|---|---|
| `BR-025` | Success status code removed | critical | A 2xx/3xx status in `from` is absent in `to` |
| `BR-026` | Success status code added | warning | A new 2xx/3xx status; clients with exhaustive handling may misbehave |
| `BR-027` | Success status code changed | critical | Exactly one success status removed and one added with an equivalent schema (for example `200` → `201`) |
| `BR-028` | Response field removed | critical | Property present in `from`, absent in `to` |
| `BR-029` | Response field type changed | critical | `schema.type` differs |
| `BR-030` | Response field became optional | warning | Property in `required` → removed from `required`; consumers may assume presence |
| `BR-031` | Response enum changed | warning | Enum set differs in either direction; new values may be unhandled, removed values may be relied upon |
| `BR-032` | Response media type removed | critical | Media type in `from`, absent in `to` |
| `BR-033` | Response header removed | warning | Header present in `from`, absent in `to` |
| `BR-034` | Required response header added | warning | New header with `required=true`; clients may not expose it |
| `BR-045` | Response field added | info | New property; additive but clients with strict validation may ignore or reject it |

**Guard:** `204` with no body and `200` with an empty schema are not equivalent; changing between them is `BR-027`.

### 3.5 Cross-cutting

| ID | Change | Severity | Detection |
|---|---|---|---|
| `BR-035` | Security requirement changed | critical | A new scheme or scope is required; a scheme is removed while another remains; the operation becomes authenticated |
| `BR-036` | Path changed | critical | Normalized path differs for the same `operationId`, including a renamed path parameter |
| `BR-037` | Referenced component removed | critical | A `$ref` used by an operation points to a component absent in `to` |
| `BR-038` | Union member removed | critical | A `oneOf`/`anyOf` member exists in `from`, absent in `to` |
| `BR-039` | Discriminator mapping changed | critical | `discriminator.propertyName` or a mapping target differs |
| `BR-040` | Array item type changed | critical | `items.type` differs |
| `BR-041` | Default value changed | warning | Normalized default differs; behavior may change without a type error |
| `BR-043` | Request media type removed | critical | A media type accepted in `from` is absent in `to` |
| `BR-044` | Request media type added | info | A new accepted media type; additive |

**Security nuance:**

- Adding a required scope → critical (`BR-035`).
- Removing authentication entirely → `warning` (security regression, not a consumer break). It is still `BR-035`, but severity is `warning`.
- Swapping one scheme for another → critical.
- Adding an optional security alternative → info.

### 3.6 Out of scope for detection

- Semantic changes that are not expressible in OpenAPI (business rules, validation performed outside the schema).
- Numeric precision changes not represented by `type`/`format`.
- Documentation quality.
- Spectral-style style violations.
- Changes to `servers[]` alone (reported as `info` metadata; base URLs are used for inference, not compatibility).

## 4. Change fingerprint

```text
fingerprint = sha256(
  br_rule_id + "|" + method + "|" + path + "|" + pointer + "|" +
  canonical_json(before) + "|" + canonical_json(after)
)
```

- `pointer` is an RFC 6901 JSON pointer into the normalized document.
- `canonical_json` sorts keys, strips whitespace, normalizes numbers, and sorts semantic sets.
- Unique per `(diff_id, fingerprint)`.
- Changing canonicalization or a rule's meaning bumps `engine_version` and requires regenerating fixtures.

### Example

```json
{
  "id": "0192f3c4-4444-7abc-8def-0123456789ab",
  "diff_id": "0192f3c4-5555-7abc-8def-0123456789ab",
  "fingerprint": "9f2c1a4b5d6e7f8091a2b3c4d5e6f708192a3b4c5d6e7f8091a2b3c4d5e6f708",
  "rule_id": "BR-016",
  "kind": "request_required_field_added",
  "severity": "critical",
  "breaking": true,
  "method": "POST",
  "path": "/users",
  "pointer": "/paths/~1users/post/requestBody/content/application~1json/schema/required",
  "before": ["name"],
  "after": ["name", "email"],
  "description": "POST /users now requires the `email` request field."
}
```

Description rules:

- Sentence case, ends with a period.
- Names the method and path.
- Names the affected field/parameter when known.
- Never includes raw YAML.
- Maximum 240 characters.

## 5. Severity decision tree

```text
Does an existing conforming consumer break?
├── yes, request is rejected or response cannot be read
│   └── critical
├── no, but behavior/guarantees change (defaults, optionality, enums, deprecation)
│   └── warning
└── no, additive or metadata-only
    └── info
```

When two interpretations exist, choose the one that a reasonable consumer generated from the previous contract would experience.

---

## 6. Versioning guidance

- Version labels are free-form strings, but the UI recommends semantic versions.
- A diff containing any `critical` change SHOULD be published as a new major version.
- BlastSpec does not enforce version numbers; it reports behavior.
- A report may be generated for non-breaking diffs; it is labeled informational.

## 7. Required fixtures

Each rule MUST have a pair of fixtures:

```text
backend/tests/Fixtures/specs/breaking/BR-001/before.yaml
backend/tests/Fixtures/specs/breaking/BR-001/after.yaml
backend/tests/Fixtures/specs/breaking/BR-001/expected.json
```

`expected.json` contains the exact change rows (rule, severity, pointer, before, after, fingerprint) so the engine is regression-tested against this document.

Additional fixtures:

- `petstore/v1.yaml`, `petstore/v2-breaking.yaml`, `petstore/v2-compatible.yaml`
- `multi-service/` with three specs and `x-consumers`
- `cycle/` for graph ordering
- `malformed/` for parser safety

---

## 8. Changelog policy

- Adding a rule: new `BR-###`, table row, fixture, engine version bump.
- Changing a severity: document the rationale, bump `engine_version`, update fixtures and snapshots.
- Removing a rule: keep the ID reserved; never reuse it.
